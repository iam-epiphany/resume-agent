# ResumeMind 系统增强路线图（2C4G 面试展示版）

## 结论

ResumeMind 已经不是“向量检索 + 一段 prompt”的初级 RAG：它已有结构化分块、dense 召回、关键词补召回、BGE reranker、查询规划、多轮记忆、答案证据分级、硬事实 grounding、流式阶段观测、限流和 E2E 评测。当前最影响体验的不是少一个高级框架，而是知识治理与指标闭环：主题元数据曾被正文偶然词误导、同一简历重复索引、历史 Qdrant 数据膨胀、评测样本太少且匿名评测拿不到检索依据。

因此增强顺序应是：先把“输入质量和测量方法”做硬，再优化热路径，最后才增加展示功能。

## 与优秀开源项目的差距和取舍

| 能力 | 优秀项目做法 | ResumeMind 现状 | 2C4G 下的选择 |
|---|---|---|---|
| 文档处理 | RAGFlow 强调复杂版面理解、模板分块、可视化人工干预 | 支持常见格式和结构化 Markdown，后台可预览 chunk | 个人材料优先整理成规范 Markdown，不引入 OCR/VLM 常驻服务 |
| 检索 | FastGPT 使用语义、全文、查询优化、RRF、rerank 多路融合，并以 token 而非固定 top-k 控制引用 | dense + 小库全文关键词补召回 + rerank；prompt 已有 token 预算 | 保留轻量混合链路；把检索评测做实，不为 119 个 chunk 引入 Elasticsearch |
| 索引增强 | Dify 增加 chunk summary index；FastGPT 可为一个 chunk 建多个精简 index | embedding 文本包含来源和章节上下文 | 先在困难问题上验证收益；必要时只为项目名、别名、数字建轻量辅助索引 |
| 数据运营 | QAnything 支持 chunk 可视化编辑、溯源、检索模式 | 可查看 chunk 和引用，缺少检索参数 A/B 工作台 | 后续增加“检索实验台”，比通用工作流画布更适合面试演示 |
| 评测 | 大型系统提供检索测试、日志和反馈闭环 | 有 350+ 单测和 E2E 脚本，但旧 JSONL 只有 6 条 | 已扩为 23 条黄金用例，并支持意图、模式、零检索、LLM 次数和延迟门禁 |
| 规模与多租户 | 大型项目面向海量文档、团队和多数据源 | 单主人公、十余篇材料 | 这是有意边界，不做租户/权限矩阵换取低资源和更短链路 |

参考：

- [RAGFlow README](https://github.com/infiniflow/ragflow)（复杂文档理解、可视化 chunk、引用；自托管建议至少 4C16G）
- [FastGPT 检索方法与参数](https://doc.fastgpt.io/zh-CN/guide/dataset/dataset_engine)（混合召回、RRF、rerank、查询优化、token 引用上限）
- [QAnything README](https://github.com/netease-youdao/QAnything)（CPU、混合检索、chunk 编辑与溯源）
- [Dify Summary Index](https://github.com/langgenius/dify/discussions/31890)（chunk 摘要辅助索引）

## 已落地的 P0 改动

- 确定性材料主题：`显式材料主题 > 文件名 > 标题/正文评分`；模糊时留空，不生成错误过滤标签。
- 所有 Markdown 增加简短 `材料主题`，未来资料转换规则写入根目录 `AGENTS.md`。
- 新增 `scripts/audit_knowledge_base.py`：检查 UTF-8、一级标题、主题、敏感信息、跨文档重复、SQLite 漂移、重复简历源、Qdrant 残留。
- 简历文字版成为唯一问答口径；上传时自动跳过同一简历 PDF。
- 2C4G 重排候选从 24 调到 12，重排输入改 compact；仍保留环境变量随评测回退。
- E2E 黄金集从 6 条扩为 23 条；管理员模式真正返回检索依据，支持 `max-p95` 与 LLM 调用门禁。

## 上线前必须完成的动作

1. 不迁移本机 `data/qdrant/`。服务器从空数据目录启动，只上传规范化 `docs/` 重建索引。
2. 当前本机运行库有 11 个旧主题标签。修改后的 Markdown 哈希已变化，重新运行上传脚本会覆盖并刷新；若要得到最干净基线，先 `--purge` 再上传。
3. 运行 `python scripts/audit_knowledge_base.py`，源文件应为 0 error；运行库重建后再次执行，`database_topic_drift` 应清零。
4. 跑 23 条黄金集并保存报告。没有报告就不要在 README 写“准确率 100%”或“p95 < 6s”。

## 建议门槛

| 指标 | 上线目标 | 说明 |
|---|---:|---|
| 文档 Recall | >= 95% | `expected_documents` 命中；先看检索，避免被 LLM 文风掩盖 |
| 期望事实命中 | >= 90% | 允许同义写法，不允许关键数字/实体缺失 |
| OOD/寒暄零检索 | 100% | 不加载本地模型、不调用生成 LLM |
| 普通独立问题 LLM 次数 | p50 <= 1 | 只保留最终生成 |
| 热态端到端延迟 | p50 <= 4s，p95 <= 6s | 受外部 LLM 网络影响，应同时记录本地 retrieval/rerank 耗时 |
| 常驻内存 | <= 3.2GB | 给 OS、Qdrant 和突发峰值留余量；配置 2GB swap 防 OOM，不把 swap 当常态内存 |
| 冷启动可用 | <= 180s | 后台预热，健康接口与模型就绪分开展示 |

## 下一阶段按收益排序

### P1：最值得继续做

1. **检索实验台**：输入问题后并排显示 dense 候选、关键词候选、融合顺序、rerank 分数、最终 prompt；支持“12 vs 24 候选”A/B。面试官能直观看到系统不是黑盒。
2. **反馈到困难集闭环**：前台赞/踩后，把问题、引用文档、回答模式和失败原因加入待审核列表；确认后才能进入黄金集，避免自动用脏反馈训练自己。
3. **阶段延迟看板**：稳定展示 embedding、Qdrant、rerank、LLM 首包和总耗时的 p50/p95；用真实报告讲优化，而不是只说“加了缓存”。
4. **证据冲突提示**：同一硬事实在多个文档出现不同值时，回答不选边，展示两个来源并提示待确认。

### P2：有数据证明再做

- ONNX/OpenVINO INT8：可显著降低 CPU 内存和推理时间，但必须用 23 条黄金集做排序一致性/Recall 回归后再切默认后端。
- chunk summary / 多索引：只对召回失败的长 chunk 启用；当前 Markdown 已按主题和标题整理，全量生成摘要可能只增加索引噪声。
- 精确答案缓存：仅缓存无 session 的独立问题，key 必须包含知识库版本、模型和 prompt 版本；知识库更新立即失效。

### 当前不建议

- GraphRAG、知识图谱、全文 Elasticsearch、VLM/OCR 常驻服务、本地大语言模型、多租户工作流画布。这些会明显超过 2C4G 预算，也不能直接提高个人简历问答的核心准确率。

## 面试演示顺序（约 90 秒）

1. 问一个明确项目问题，展示 fast path：1 次 LLM、引用片段、rerank 分数和 grounding 结果。
2. 连续追问“那为什么不用数据库锁”，展示会话指代消解。
3. 问“你的银行卡密码”，展示 0 检索、0 LLM 的安全转移。
4. 打开评测报告：23 条黄金集、文档 Recall、事实命中、p50/p95、LLM 调用次数。
5. 最后解释取舍：RAGFlow 至少建议 4C16G；本系统在 2C4G 上用小库确定性治理和可测量链路换取低延迟与可信度。
